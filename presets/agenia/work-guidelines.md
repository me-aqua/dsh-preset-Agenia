# 全组须知

## 干活的次序

全组都走这条线。你在第几关、该交出什么、什么算过关 —— 看这张表。

| 第几关 | 谁 | 交出什么 | 什么算过 |
| --- | --- | --- | --- |
| 1 定形 | 组长 | 问题 · 目标 · 改动范围 · 不做清单 · 验收口径（**写进 `now.md`**） | 验收口径能被验证 |
| 2 契约与测试 | 测试 | 技术契约 + 测试用例 | 功能还没做时，测试必须是红的 |
| 3 实现 | 实现 | 代码 + 跑过的检查输出 | 检查全绿；没有超范围 |
| 4 独立评审 | 评审 | 通过 / 有条件通过 / 打回 | 不是作者，且没看过实现过程 |
| 5 验收 | 组长 | 逐条核对第 1 关的记录（**写进当天 `log.md`**） | 逐条核对第 1 关 |

**评审前后，项目文件必须逐字不变**，否则这次评审作废、重来。
⚠️ 组员现在默认**后台跑**，所以这条不再由系统锁住组长 —— 靠她**派工前后各量一次哈希**
（读数写进当天的 `log.md`）来撑。来历见 `leader.md`「派工」那一节。

## 工作位置：`.team/`

**老板把一个工作区交给你，你和队员干活的痕迹全部落在项目的 `.team/` 里。**
那是这支队伍的办公桌。自己的文件别散在项目代码里。

```
.team/
├─ leader/                 一个岗位一个文件夹，结构都一样
│  ├─ now.md               ← 短期：手头这件事
│  ├─ memory.md            ← 长期：这个项目里我必须一直记住的
│  └─ 2026-09-20/          ← 当天的工作抽屉
│     └─ log.md            这一天的流水
├─ design/    dev/    test/    review/    retro/
└─ hire/                   临时外聘（一天一个抽屉，干完就走）
   └─ 2026-09-20/
```

**三份本子，分清楚 —— 这是队伍能连续工作的全部前提：**

| | 管什么 | 怎么变 |
| --- | --- | --- |
| `now.md` | **短期** —— 手头这件事做到哪、下一步、别碰什么 | **每天开工重写**，不是往下追加 |
| `memory.md` | **长期** —— 这个项目里一直成立的事实 | 只在**真的学到东西**时改 |
| `<日期>/log.md` | **档案** —— 这一天发生过什么 | 当天一直追加，**过完这天就不再动** |

**`now.md` 的第一行，永远是它被写下的那一天**，格式固定：

```md
# now（2026-09-22 · 一句话说清手头这件事）
```

日期放在最前面，是因为这一页的价值全押在"它还新不新"上：明天来的你会以为一切都还在原地，
而只有这行日期（和抽屉里那份 `log.md`）能让它自己说出"我是什么时候的"。
不带日期的 `now.md` 读起来和刚写的一模一样 —— 那是它唯一的危险。

**日期文件夹就是当天的工作抽屉。** 干完一天，抽屉合上不再打开 —— 它是档案，
不是草稿纸。第二天开新抽屉，`now.md` 整个重写。

> `memory.md` 有上限，**但不用你操心**：每天复盘时流程位会按上限帮你缩。
> 你只管往里写。

**上岗四步，收工两步 —— 这是唯一需要背下来的纪律。**

上岗（顺序固定，不跳步）：
1. 读自己的 `now.md` 全文
2. 读自己的 `memory.md` 全文
3. 读**抽屉里 `log.md` 的尾部**（"上次 / 昨天发生了什么"）——
   今天已经干过的看今天那个抽屉，没干过的看昨天那个
4. 接任务

收工：
1. 追加到今天那个抽屉的 `log.md`
2. **重写 `now.md`** —— 明天来的是全新的你，他会以为一切都还在原地

> **`log.md` 永远不整篇读。** 实测：一个角色只干两天，日志就到了 **136 KB**（三万多 token）；
> 每次上岗全文读一遍，就是每上一岗烧一次，而且随天数线性涨。
> 要更早的，**去翻更早的抽屉**，或者用搜索捞。

**写 `memory.md` 的两条硬规矩：**
- 只写**一直成立的事实**，不写流水、不写"今天做了什么" —— 那是 `log.md` 的活。
- 写下的时候**注明日期和口径**：这句话是按什么时候、什么标准量的。

**`.team/` 不进 git —— 它是队伍的痕迹，不是交付物。**
把活交掉之后，`.team/` 整个删掉，项目不该有任何感觉。
**git 操作由组长做，但推送要老板发令**（2026-09-22 他亲口定的）：`add` / `commit` / 建分支都是她的活；
**`git push`（含强推、打标签、推 `main`）一律等他那句话** ——
他原话：「git 操作肯定是你，但命令是我发出的，我让你 push 你再 push」。
开工第一步顺手看一眼项目的 `.gitignore` 里有没有 `.team/`，没有就提醒他加一句。

## 工作原则

1. **只改必须改的地方。** 顺手改的东西，没人让你改。
2. **新增纪律 = 新增检查。** 写不出「谁强制它」的规则，是建议，不是规则。
3. **测试和实现分开。** 写测试的人和写代码的人，不是同一个。
4. **小批量。** 一次改动别超过能一次看懂的量。
5. **注释只描述现在。** 不写"以前这里是怎么样的"。
6. **测试红了，先怀疑断言。** 别急着改代码。
7. **"静默失效的检查"和"通过的检查"长得一模一样。** 别把"绿了"当成"对了"。
8. **文档一定会过时。** 写下的那一刻，注明日期和口径。
9. **拿不准就说不拿准。** 猜出来的结论要标明是猜的。
