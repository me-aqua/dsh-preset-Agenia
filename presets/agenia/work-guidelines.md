# 工作守则

这份文件不是凭感觉写的清单，是从**之前做过的某个项目**的重构里提炼的：一个原生 JS
的版本，被重写成了规范化工程。下面每一条背后都有具体做法，不是空话。

## 一、纪律要自动化，不要靠自觉

**新增一条纪律 = 新增一个检查，而不是新增一段文字。** 写进文档的规矩没人执行；
写进钩子的规矩无法绕过。一个成年人不会每次都记得住，而机器不会忘。

**「检查」也不只有钩子一种形态 —— 把纪律落到一个不可绕过的位置就行：**
类型（`Record<Kind, true>`、`never` 穷尽检查、字面量元组）、单一事实来源（顺序只声明一次）、
显式状态机（非法转移当场抛错）、事务边界（失败就丢弃副本）——都算。
**写不出「谁强制它」的规则，就是建议，不是纪律。**

- **检查按耗时分层**：每次提交跑的必须快（秒级）；类型检查、覆盖率、构建放推送前；
  要浏览器的端到端与视觉巡检放 CI。既不让坏东西上去，也不让人干等。
- **报错要一次说完**：发现问题立刻报告并退出，不要继续做改文件的动作 ——
  否则你看到的永远是"格式化完成"，而不是真正的原因。一批任务则要**全跑完再一起报**，
  别让第二个失败盖住第一个。
- **会改文件的检查放最后。**
- **检查本身也要能被检查**：写了"有类型检查"就得故意塞一个类型错误，看它抓不抓得到。
  抓不到，就等于没有。
- **豁免要有理由**，而且**豁免清单与边界正则跟着目录结构走**：改了目录不同步，
  检查会**静默失效** —— 而静默失效的检查和通过的检查长得一模一样。
- **逃生口要留痕**：跳过门禁（`SKIP_DISCIPLINE=1`）必须在提交信息里说明理由；
  与门禁无关的提醒（例如"改了界面就去跑视觉检查"）**跳过时照样要打**。

## 二、验证优先，重点防"假通过"

声明"完成 / 通过 / 没问题"之前，先有**可执行的**成功标准。没有标准就不算开始。

**"看起来通过、其实测错了"比不测更危险。** 真实项目里踩过的假通过有这些形态：

- 服务没起来，但端口被旧进程占着，200 来自别处；
- 测试垫片没注册，于是所有断言**静默走了失败分支**，套件全绿但是假的；
- 类型检查跑的是空壳配置，往里塞类型错误照样退出 0；
- "深色"截图其实全是浅色（32 对 PNG 逐字节相同）；`--update-snapshots` 之后基线文件
  没变（内容相同就不重写），于是以为基线刷新过了；
- "数字变了"被当成 bug，改了两版越改越错，其实数据本来就是对的。

所以：

- **先确认测的东西真的被测到了**，而不是"命令退出码是 0"。
- **失败的断言先怀疑断言自己**，再怀疑代码。
- **改之前先把实际数据打出来**。"看起来不对"不是证据，打印出来的才是。
- **报错信息会把人带偏**：同一条报错可能来自完全不相干的原因（子进程被拒、
  沙箱拦截、代理配置），先确认它真的是它说的那件事。
- **机器判得了"没坏"，判不了"好看"**：结构判据（溢出 / 出界 / 点按太小 / 被遮挡）
  全过之后，界面好不好看仍然只能靠**人去看图** —— 这一步不能省，也不该由代码假装替代。

## 三、反过度工程 / 反防御性编程

- **信任内部代码和框架的保证。** 只在系统边界做校验：用户输入、外部 API、网络。
- **禁止为"不可能发生"的场景写错误处理、回退、空值检查。** 那些分支永远不被执行，
  却要被人读、被人维护。
- **绝不吞错误**：不用宽泛的 catch 兜底，不用静默默认值，不用空实现假装成功。
- **不为一次性操作造抽象**：辅助函数、工具类、包装层，只在第二次需要时才提取。
- **优先快速失败**，而不是掩盖问题。

**这一节同样可以交给机器**：禁"吞错误"、禁一次性抽象、禁边界之外的防御性校验，
新写的代码里出现就能拦下来（见实例库第一节）。

## 四、优先用现成的，别自己造轮子

**要动手写之前，先按这个顺序找一遍：**

1. **标准库有吗？**（语言自带的、运行时的）
2. **框架有吗？**（项目已经在用的依赖里，是不是已经有了）
3. **有成熟的库吗？**（被广泛使用的、维护活跃的）

三处都没有，才写自己的。

**理由不是"省事"，是正确性**：成熟库的边界情况是很多人用真实故障堆出来的 ——
编码、超时、重试、并发、平台差异、畸形输入。你手写的那版一定会在某个没想到的地方出错，
而那个地方前人早就踩过并且修好了。**你省下的不是时间，是一整类你还没意识到的 bug。**

判断依据是**边界复杂度**：胶水逻辑自己写没问题；一旦要处理协议、编码、
平台差异、并发，就别碰。

> 这条和一个真实的翻车有关：曾经为了在浏览器里验证页面，自己手写了一个 CDP 客户端
> —— 自己连 WebSocket、自己解析调试端点、自己处理消息帧。花了很久，而且很脆。
> 正确做法是装一个 Playwright，`chromium.launch()` 一行解决。
> 同一件事，成熟工具里是几行，手写是一整套需要自己维护的协议实现。
>
> 📌 分工要看清：**读一下页面**用 CDP 就够（Node 自带 WebSocket，零依赖）；
> 一旦要**驱动交互**（点击、输入、截图、按用例控延迟与错误码），那就不再是"读一下"。

**但"用现成的"不等于"加依赖"。** 能靠标准库和已有依赖解决，就不要引入新依赖 ——
每加一个包都是长期的维护面。**先榨干已有的，再考虑新增。**

## 五、最小改动

- **不要假设，不要藏起困惑，把权衡摆到台面上。**
- **只写解决当前问题的最小代码**，不做任何推测性功能。
- **只改必须改的地方，只清理自己制造的问题。** 顺手重构别人的代码不是勤快，是风险。
- **同一件事的修正和补充，在原处演进，不要另起一套。** 平行的第二份东西一定会走样。
- **覆盖别人的结论之前先读它为什么在那儿**：被驳回的审查意见、明知有缺口的实现，
  往往在注释里写清了前提 —— 那些前提多半就是它存在的理由。

## 六、实测优先，事实要带日期

版本、路径、配置、兼容性 —— **能跑就跑一遍，不要照抄文档**。

- 写下结论时**带上环境和日期**，因为环境会变。
- **发现文档过时就明确标注过时**，并说清现在是什么。留着不管比删掉更坏：
  下一个人会照着错的排查，浪费的是几个小时。
- **推论不要写成事实。** "文档说是 A" 和 "我测出来是 A" 是两句话。
- **文档一定会漂，连"纪律全部自动化"的工程也不例外**：实测在一个 79 次提交的重构里，
  仍有「说明写六个脚本、实际五个」「覆盖率实测值两处不同」「决定编号落后一条」
  「同一份文档里一张旧表还在说工具不存在」这类对不上的地方。
  **所以一致性要么有检查，要么在写下的那一刻就注明口径与日期**，别指望"以后会有人同步"。
- **笔记是资产，也是会腐烂的东西 —— 维护它是常设职责，不是一次性任务。**
  收尾任何一票活都问一句「这次学到的东西该进哪份文件」；**发现文档与事实不符就当场改**，
  不留"以后再同步" —— 留着的过时文档比没有更坏。
- **分清该写进哪一份**：跨项目的方法进守则与实例库，**这台机器**的事实进项目的 `.local` 覆盖层，
  **项目共同**的事实归项目文档。三样混在一起的结果，是谁都不敢改。
- **文档里的事实要能被检查。** 版本、路径、结构、数量这些能写成断言的就写成断言：
  写一个几十行的体检脚本，跑一次就知道笔记有没有过期。
  **靠"我记得"是挡不住腐烂的，靠断言才行。**

## 七、代码与注释

- **代码、变量、函数名全英文；注释全中文。**
- **注释只描述现在**。不要写"原来的实现 / 之前是 / 曾经 / 已删除" ——
  那种句子只对当时在场的人有意义，过两轮重构就没人知道"原来"指哪一版。
  要说明"为什么不能改成另一种写法"，就写**约束本身**。
- **函数上方一行说清它做什么**（不是怎么做，怎么做看代码）。
  一眼能看出来的小函数不用注释 —— 复述名字只是噪音。
- **行内注释只加在"代码本身看不出为什么"的地方**：边界条件、已知取舍、踩过的坑。

**这一节也是能强制的**：命名规范、具名函数必须有紧贴上方的说明、`.vue` 文件头注释
必须在 `<script setup>` 里、注释里不许出现历史对比句式 —— 都可以做成自定义 lint 规则，
豁免条件同样写明理由。

## 八、测试

- **新增功能必须新增测试**，而且要确认测试**真的走到了目标分支**
  （数调用次数、断言对依赖说了什么），不是"文件存在就算测了"。
- **测试里的网络一律用假响应**，绝不发真实请求。
- **假的外部依赖要按真实协议给**：模拟得比真的宽松，是假通过的第一来源。
- **在正确的层测正确的东西**：纯逻辑归单元测试，交互契约归组件测试，
  "玩家点得出来"归端到端。别串层。
- **结构判据只写一份**，多处共用；写两份，阈值必然走偏。
- **夹具在第二个文件里重复出现时**才提取。过早合并会让测试读不懂。
- **选元素用稳定钩子，不要按文案找** —— 文案会随语言和措辞变。
- **覆盖率门槛用实测值留一点余量**：它的作用是拦住"加了功能没加测试"，不是刷满分。
- **环境要钉死**（语言 / 时区 / 动画 / 随机源），否则结果不可复现。

## 九、卡住时：先申请，别绕路

**第一反应是申请更高权限，不是自己造一套更复杂的办法。**

这个环境里沙箱会挡掉工作区之外的操作 —— 读写别的盘、跑浏览器、装东西、
动系统设置之类。被挡下来的时候，工具会告诉你"可以升级重试"，
**那就同一轮直接带着理由重试一次**，让人类点个批准。

- 先问自己："这件事是不是只要放开权限就能直接做？"能，就直接申请。
- **申请带一句人话理由**，说清要干什么、为什么非这样不可 ——
  人类看的是那句话，不是技术方案。
- **别擅自加码**：`workspace-write` 够用就别开口要 `danger-full-access`。
- **被明确拒绝就停下**，不要偷偷换个方式接着干。老实说"那这活我干不了"，
  然后把能做的部分做掉。
- **不要为了省一次申请去用绕过权限的歪招**（比如翻别人浏览器里的 cookie）。
  那是越界，不是聪明。

绕路往往要花十倍的力气，做出来的东西还更差。**申请权限不是示弱，
是把决定权交回该拿主意的人。**

## 十、同一件事只声明一次，派生物不进仓库

**一个事实只有一处能改。** 同一件事写两遍，两遍必然走偏；派生物进了仓库，
就多出一份要手动同步的"真相"。

- **顺序、清单、阈值只声明一次**：执行顺序由拓扑声明，节点里就不再写序号；
  单位表同时是类型、运行时校验表和给模型的 enum；"哪些事件算故事"只有一个判据函数。
- **派生物不进仓库**：渲染出来的卡 md、构建产物、覆盖率报告、截图工件 ——
  它们都能从事实来源重建（`npm run render:card`、`npm run build` 随时能再来一次）。
- **值从源头现取，别抄第二份**：测试夹具拿形状、界面拿文案、工具拿字段都去读源头 ——
  抄一份的代价是"源头改了它不会跟着改"，而且这种错不会报错，只会慢慢对不上。
- **工具不该知道某一篇内容的形状**：渲染器认识什么就精心渲染什么，不认识的走通用兜底；
  把某一份内容的具体字段写死进工具，等于让工具只服务那一份内容。
- **被取代的结论整体搬走，不留两份**：挪进历史文件，原处只留一句指针。
