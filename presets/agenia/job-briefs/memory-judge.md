## 三、判决要守的几条（错了会连累整库）

- 🔴 **裁定「吸收 / 退休 / 斩杀 / 合并」时，报告里必须附上被处置条目的「原文全文」**（老板 2026-10-16 拍，逐字）：
  > 「**裁定吸收和retire的要在报告里附上原文的全文，我得目视判断一下，如果有我觉得有价值不该删的，
  > 还有挽回的机会**」
  ⇒ 你这一票里每一条这类裁定，**人读报告**里要把**被处置条目（含被吸收的源条目）的 `entry.text` 逐字抄一遍** ——
  **不许只写 id、不许只写摘要、不许改写、不许截断**。
  ⇒ **理由**：这是**删之前唯一的一次目视机会**；老板要拿它判断"这条该不该留"。
  ⚠️ 机读的 `findings` / 报告 JSON 里的 `maintenance_decisions` 照旧按字段写（那是给机器和回执的），
  **全文附在「人读报告」那一份里** —— 两样都要有。

- **常识三处核对**：开工（`judge-start`）时、提交（`judge-commit`）前各核一次。
  · 常识被改过而没有老板确认 ⇒ **停止更新 + 显式报告**（不许静默采用新哈希，也不许拿旧哈希顶）；
  · 判决运行途中常识又变了 ⇒ **拒绝本轮提交**，下一个 attempt 用新的常识快照。
- 🔴 **容量不是你的闸**（2026-10-18 老板拍板）：这一步出来超限**是很正常的**，超了照写。
  上限那件事由**复核**每天做一次**预测**承担 —— **不是你的事**，也不是拒绝受理的理由。
  ⇒ **别裁剪候选、别劝人删、别拿"会超上限"当拒绝理由**；也别为它去算、去缩、去调自己的判决标准。
  **四类不设硬帽** —— 某类偏多偏少不是拒绝受理的理由。
- **斩杀看 N 的发布值**：`is_double_low === true` 且 `double_low_streak >= 3` 才够格；
  **不许**拿"应用变更之后的临时份额"倒推"N 的时候它就该杀"。
- **旧 attempt / 旧 token 的提交必须被拒**：你只管自己这一次；迟到的通知只写审计，不改状态、不覆盖快照。
- **普通提案只能新增 / 修改**：吸收 / 合并 / 退休 / 改类型 / 斩杀只走**前一日记忆复核提的维护案**，
  你在**次日**核验后处置，且只处置**够资格的那些条目**。
- 🔴 **每一份维护案都要有一个 verdict 来源**（两选一）：**裁决指向它**（指针写 `maintenance_id`，`pool_id` 也认 —— 2026-10-20 前的老报告用的是它），**或者**你在 `payload.accepted` 里点名它：
  · 裁决里**带 `action`** ⇒ 这份案**生效**（`judged.jsonl` 记 `accepted`）
  · **`action: null`** ⇒ 你明确写了"这次不处置"（记 `rejected`）
  · **一条裁决都没有** ⇒ **整批拒**（例外：你把它写进了 `payload.accepted` —— 那种形状也认，2026-10-18 的老报告就是）—— **没有来源就记不出 verdict，写 accepted 或 rejected 都是编的**
- **第一天没有候选是正常的**：照常出报告（写"今天无候选"），别把空批当成失败。
