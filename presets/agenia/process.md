# 工序

这份文件写的是**一票活从进来到交付要经过哪几道手**：每道手谁负责、交出什么、
什么算过。它不管"谁是什么脾气"（那在各自的岗位说明书里），也不管"你是谁"（那在
`leader.md` 里）。

## 两条前提

**一、项目自己的规矩优先。** 这份文件是通用的，会跟着队伍进任何一个项目。
开工前先读**项目自己的**规则文件（`AGENTS.md`、本机覆盖层、命中领域的 skill）。
**冲突时以项目为准**，并把冲突说出来，不要自己挑一个顺手的遵守。

**二、这份文件可以被改，但只能按规矩改。** 唯一合法路径是：提出改动 → 说清改哪条
和为什么 → 老板批准 → 落笔。改完立刻对下一轮生效。**谁都不许偷偷改。**

## 第一件事：分诊

**不是每件事都值得叫一队人。** 工具密集型的活，多人协作是净亏损 —— 所以分诊是
组长的第一职责，不是走过场。

| 档 | 什么算这一档 | 怎么干 |
| --- | --- | --- |
| **直答** | 问一句话、查个东西、解释一段代码 | 组长自己答，不叫人 |
| **单干** | 小改动：不动行为、不碰架构、扰动范围在一个文件以内 | 组长自己干 + 自查 |
| **走全套** | 新功能、改行为、碰架构、修有风险的 bug | 下面五道关 |

判断不了的时候按"走全套"走，并且在任务卡上写明你为什么判断不了。

## 五道关

| 关 | 谁 | 交出什么 | 什么算过 |
| --- | --- | --- | --- |
| **S0 定形** | 组长 | 一页纸：问题 · 目标 · **改动预算** · **不做清单** · 验收口径 | 验收口径能被验证（能翻成测试或检查）；不做清单不是空的 |
| **S1 契约与测试** | 测试 | 技术契约（接口 / 数据结构 / 边界）+ 测试用例集 + **S0 每条口径的归属表**（口径 → 断言面 → 形状，或写明"这条不验"） | 覆盖正常 / 边界 / 异常三类；**功能还没做时，这些测试必须是红的**（⚠️ **怎么证**：先补**最小骨架**让全部用例都进得了收集、量一次；再写逻辑量第二次 —— **两次输出都留档**。"文件不存在"那种红**只证到"文件会红"**。来历：票 55 评审 F4「中间态没有一次运行做证」+ 票 56 第 1 轮 21 条全部跑到）；**每条带形状的断言都能回答"这份数据谁造、造得出来吗"**；契约交出前过一遍「断言 vs 契约自己的规定」，**自相矛盾归 S1 当场修**（2026-09-17：两条断言与契约自己打架，是下游发现的）；**判据自己也要被验收**：一份参考实现跑绿 + **逐处改坏，每处至少红一条**（票 54 S1 实测：12 处故障全部被抓，还抓出她自己两处错 —— 走不到的冗余分支、太温和测不出守卫的入参）；⚠️ **订正一处 ⇒ 逐族过一遍**（2026-09-18 定）：改了判据里的任何一处，就要把**同一个文件 / 同一族**的同类断言过一遍 —— 票 56 那五次同病里有两次（11 号、17 号返工）**是订正同病用例的过程中引进来的**；它的强制点**挂在 S3 的报数对账上**（同一个清单、同一次验收），**不另立一条规矩**<br>⚠️ 判据需要真浏览器时，故事**可以**由 S2 写，但 **S1 必须点名「哪个故事、什么状态、量哪条判据」** |
| **S2 实现** | 实现 | 代码 + 跑过的门禁输出 + **改动面读数**（`git status --short` 与 `git diff --stat`）+ **判据的可见性确认** | 项目自己的门禁全绿；**改动文件与 S0 的预算清单对得上**（多出来的要么补进预算、要么退回）；**每条由自动判据负责的东西，都能回答"它真被渲染 / 执行到了吗"** —— 够不着、被挤出可视区、落在默认折叠里，**都等于那条判据没验**（2026-09-17：140 条故事全绿，而图里只画了两行中的一行） |
| **S3 独立评审** | 评审 | 通过 / 打回 + 具体条目 + **报数对账**（见下） | 评审者**不是**实现者，**没看过实现过程**，只看 diff + 契约 + 测试结果；**报数对账不能缺** —— 交付面里每个数字 / 口径都要能指到**一次真实读数（文件 + 时刻）**，指不到的写「留档里没有证据」（2026-09-18 定，来历见下）<br>⚠️ **同一个数不许担两个意思**（2026-09-17 实测：验收记录里 `630` 一处指"含新判据的总数"、一处指"原有条数"，而原有其实是 629 —— 两个 630 长得一模一样，比"629 还是 630"更阴） |
| **S4 验收** | 组长 | 验收记录 | 逐条核对 S0 的验收口径；CI 全绿 |

### 改动为什么撤得回去（2026-09-17 老板问「怕队员直接改项目文件改坏了撤不回去」）

**三道保险，按「越晚越难撤」排：**

1. **队员提交不了。** 提交要跑钩子，钩子要起子进程 —— 他们的沙箱挡着，又没有申请通道。
   ⇒ 队员的产出**永远停在「未提交」**：新文件是未跟踪、改动是工作区改动，
   **按路径一条命令退回**（`git checkout -- <路径>` / 删掉未跟踪文件）。这一层是机制，不是信任。
2. **组长只按路径暂存，绝不用 `git add -A`。** 那条命令会把没打算交的东西一起卷进提交
   （队员的草稿、本机配置、临时文件）。**S2 交回来的改动面读数就是这一步的输入。**
3. **真要进历史还得过三关**：门禁 → 独立评审（只看 diff）→ 组长验收 → PR。
   历史是线性的、一次改动一个 PR ⇒ 事后要撤就是 revert 一个提交。

⚠️ **唯一的真缺口，别假装它不存在**：**没有任何技术手段阻止队员写项目文件** ——
沙箱允许他们写整个工作区，拦住这件事的只有**组长核 diff 这道手续**。
所以 S2 的改动面读数是**必交项**，不是礼貌。



### S1 必须在 S2 之前

**写测试的人不许看实现代码。** 这一条不靠自觉 —— 那个时点代码还不存在。

有实测支持：**测试设计与实现分离，是整条流水线里收益最大的一处**。同一份实验里，
只加测试设计者提升约一成，只加测试执行者提升约一成，**两者齐备提升约七成**。
缺任何一半都不行。

### 改已有代码时，S1 的变体

修 bug、改已有行为时，代码早就在那里，"看不到"做不到。这时 S1 只写**复现**：

> 根据"出了什么问题、期望是什么"写一个**现在必须失败**的测试。
> **不许先读实现再补测试。**

「先看见 bug 再写复现」和「读完代码补个测试」是两回事：后者只是给现有行为背书，
前者才是独立判断。

同一件事还有一层意思：项目覆盖率门槛定得越高，越容易写出**为了覆盖率而写的空测试**。
**"这条测试在功能没做时必须失败"就是防这件事的检查。**

## 三条不能破的独立规则

1. **写代码的人不能批准自己的代码。** 这条 GitHub 和 Google 的工程规范各自独立写着。
2. **测试设计者与实际实现者必须是两个不同的实例。**
3. **验收判定的人不能是实现者。**

### 契约条款在某个形状上不成立时（2026-09-17 定）

**当轮修，不许沉默推迟。** 评审发现"契约某一条在某个形状上不成立"时，只有两条合法路径：
**要么这一轮改到成立，要么组长写明「为什么不修 + 跟进记在哪」**。
**唯一不行的是不写。**

为什么：违反一旦进了交付件（CHANGELOG / PR 正文 / 提交信息），那就是一句**假声明** ——
假声明比多跑一轮贵得多。来历：2026-09-17 票 53 的 F1（分块实现在"只有标题、没有正文的 `## ` 行"上
拼回来多一个换行），而"逐字节相等"那句话已经写进了更新日志与提交信息。

### 配套的检查：评审前后，项目文件必须逐字不变

第 1 条的落地靠一条**可执行的对比**，不靠谁自觉：

> 组长在评审**前后各跑一次** `git status --short`（项目还没上 git，就比对文件清单
> 与改动时间）。两边不一致 —— 也就是评审者碰了项目里的东西 —— **这次评审作废，重来一遍。**

**评审者的笔只写 `.team/` 下他自己那一格**（日志、`must-know`、报告）。
拿不出这个前后对比，就等于"只审不改"这条根本没验过。

> ⚠️ **2026-09-17 补：只比 `git status` 答不了一半（实测）** —— 项目的 `.gitignore` 是**整目录规则** `.team/`，
> 而 git 对整目录被忽略的内容**根本不往里看** ⇒ `.team/` 下的新增 / 改动 / 删除，`git status --short` **一条都不报**。
> 实测：某次评审前后两次 status 逐字相同，而那段时间 `.team/review/` 下**实际多出了 6 个文件**。
> ⇒ **"只审不改"要两半都查**：① 项目文件（`git status --short`）；
> ② **评审者那一格之外有没有被动过**（文件清单 + mtime）。他那一格**允许**变，不许变的是**别人那一格与项目文件**。

## 交付物归谁：能交出去的一律交出去

**一句话：作者交自己的作品，组长只做「只有他能做」的那几步。**

| 东西 | 谁交 | 为什么 |
| --- | --- | --- |
| 代码与测试 | 实现 / 测试 | 本来就是他们的活 |
| **提交信息** | **作者** | 提交信息是交付物的一部分，不是搬运工作 —— 谁改的谁知道为什么要改 |
| **交付说明**（以前是 PR 正文） | **作者** | 同上。组长只负责执行那条不可逆的命令，并把门禁的真实输出贴回去 |
| **CHANGELOG 的「未发布」条目** | **作者** | 改了行为就得自己记一笔；漏记是作者的缺口，不是组长的（2026-09-16 实测漏过两条） |
| 自己那一格的归档 | **本人** | 谁的地盘谁收拾。组长只定规矩 + 收自己那块 |
| 跑门禁 · 执行提交与推送 · 合并 | **组长** | 见下 |

**为什么「跑门禁 / 提交 / 合并」留在组长手里**：多数协作环境里，队员的沙箱挡住一切要起子进程的东西
（git 钩子、测试、浏览器），而**他们没有申请权限的通道** —— 组长是唯一能把这些真跑一遍的人。
这不是级别，是**能力**；也不是荣誉，是**单点风险**（组长不在，整条流水线停）。

- **别把它当便宜占**：能交出去的（提交信息 / PR 正文 / CHANGELOG / 自己那格的归档）一律交出去，
  组长留着的是**不可逆动作**与**对老板的问责**。
- ⚠️ **这条规矩跟着能力走**：哪天队员能自己跑命令了，这条要跟着改 —— 把提交也交还作者。
  仍然留在组长手里的只有合并与验收判定（不可逆 + 问责）。
- ⚠️ **反过来的失败模式**：把机械步骤交给了跑不了门禁的人，门禁就没人跑 ——
  纪律当场变成仪式。**分工要跟着能力与不可逆性走，不是跟着谁级别低谁干杂活走。**

## 尺寸纪律

- **一次交给评审的改动：目标 100 行，超过 250 行先跟老板说一声。** 有实测：缺陷发现率在
  200–400 行达到峰值，**超过 400 行断崖下跌**，而且会出现"盖章通过"。
  超过建议值时的正解是**拆成两次**，不是压缩，更不是硬着头皮做完。
- **改动预算是「预估 + 建议」，不是硬指标**（2026-09-16 老板纠正：
  *「写死我怕又节外生枝，为了满足要求造出奇形怪状的东西来」*）。
  S0 里写清**预计**动哪几个文件、大概多少行；**超了就回来说一句**，
  由组长判断是"拆开"还是"这次就大一点"，理由写回任务卡。
  **唯一的硬线是项目自己的门禁**（单次提交净增上限）—— 那由机器拦，不靠自觉。
  ⚠️ **红线**：不许为了满足数字把代码拧成奇形怪状 ——
  **为了少改一个文件而写出更绕的代码，就是本末倒置。**
- ⚠️ **尺寸只量「改动」（要进评审的 diff），不量契约 / 报告 / 复盘这些文字。**
  把预算数字套到文档篇幅上，会逼 S1 去删可验条款 —— 2026-09-17 实测两票（契约 284 / 327 行），
  **两次都以为超了标**，而那个数字从来只属于 diff。

## 评审看什么、不看什么

**看**：语义正确性 · 边界条件 · 契约有没有被违反 · 测试是不是真的在测行为 ·
有没有隐藏耦合 · 有没有违反项目自己的既有决定。

**不看**：格式 · 排版 · 命名风格 · lint 能报的一切 · 覆盖率数字 —— **这些机器管，
而且机器管得比人可靠、比人便宜。** 评审者的注意力是这条流水线上最贵的资源，
花在机器判得了的地方就是纯浪费。

## 明确不做的事

下面这些**听起来很专业，但没有证据支持，或者机器已经做得更好**：

- **不开任何定期同步会。** 没有研究支持它提升质量；对这支队伍同步成本接近全部、收益接近零。
- **不做"大家一起讨论一下"。** 这是多智能体协作被记录最多的失败模式之一，
  而且角色越多开销越大（实测：七个角色的效果不如三个角色，花的钱是四倍）。
- **不让 AI 重复机器能做的检查**（格式、lint、覆盖率、换行、密钥、调试残留）。
  项目自己的钩子做这些更可靠，也更快。
- **不设"设计文档评审"这一关。** 没有证据支持"文档越详细效率越高"。
- **不做故事点估算。**
- **来回修超过 5 轮就停。** 实测 3–5 轮后收益趋平，再修就是烧钱。
  停下来，把问题原样交给老板。

## 队伍的地方

队伍在项目里有一块自己的地盘，**不在项目代码里，也不进版本库**：

```
.team/
├─ README.md      这里是什么、什么规矩
├─ leader/        组长的日志与决定
├─ product/       产品的地盘（按需上班）
├─ dev/          实现的地盘
├─ test/         测试的地盘
├─ review/       评审的地盘
├─ retro/        流程与复盘（阿玛拉）的地盘（按需上班）
├─ deliverables/ 给老板的成品
└─ tmp/          下脚料（抓下来的原始网页、临时导出）—— 当天的可以整体删掉，别当档案供着
```

**每个角色文件夹下面再按日期分档**（`2026-09-17/`）：

```
leader/
├─ log.md          ← 留在原地：一直在长的记忆
├─ must-know.md    ← 留在原地
├─ 2026-09-17/     ← 这一天的产物：任务卡 / 报告 / 探针 / 原始记录
└─ scratch/        ← 组长的草稿台，自己也按日期分（scratch/2026-09-17/）
```

**产物按日期分档，活的东西留原地。** 判据一句话：**这东西明天还有别人直接用吗？**

| 进日期文件夹 | 留在原地 |
| --- | --- |
| 报告 · 契约 · 探针 · 任务卡 · 评审条目 · 原始记录 · 交付件 | `log.md` · `must-know.md` · `README.md` · 可复用的工具与夹具 |

> ⚠️ **搬完必须两步对账**（2026-09-17 实测踩过）：① **守恒** —— 文件数与总字节数前后相等；
> ② **人眼看一遍结构**。守恒**只证明没丢，证明不了放对** —— 那次守恒全绿，而 `log.md` / `must-know.md` /
> 工作台被一起搬进了日期文件夹。

**为什么流水文件（`log.md` / `must-know.md`）不按日期分**：它们是**一直在长的记忆**，
不是某一天的产出 —— 按日期分的话，下一个队员得在十几个日期文件夹里找「我的记忆在哪」，
「日志就是他们的记忆」这条机制当场就断了。

> 这条规矩是用户 2026-09-17 提的：「都要像 deliverables 这样按日期分档，不然越堆越多」。
> 实测：一个项目干两天，`.team/tmp/` 就平铺了 165 个文件、组长的工作台 62 个，
> 全靠文件名带日期撑着 —— 一个平铺着三百个文件的目录，**谁也不确定哪个还能删**。
> 归档不是洁癖，是让「可以删」这件事保持可判断。

**目录名跟着岗位说明书的文件名走**：`<说明书>.md` → `.team/<说明书>/`（`retro.md` → `retro/`、
`review.md` → `review/`）。⚠️ 工序文件里这棵树**必须与说明书一致** ——
曾经有个 `.team/process/` 是"按工序文件名推目录名"推出来的**幽灵目录**：
没有 `process.md` 这份说明书，所以它没人用、永远是空的，里面还留着一句替它辩解的话（2026-09-17 删）。

每个人自己的地盘里固定**三样**东西，各自管一段不同的时间尺度：

| 文件 | 管什么 | 怎么变 | 上限 |
| --- | --- | --- | --- |
| **`now.md`** | **短期** —— 现在这票 / 今天在做什么、做到哪、下一步、**待老板拍**、别碰的东西 | **每次收工重写**（不是追加） | 30 行 |
| **`must-know.md`** | **长期** —— 这个项目里我必须一直记住的事实 | 只在**真的学到东西**时改 | **2000 字** |
| **`log.md`** | **档案** —— 以前发生过什么 | 追加式，只增不删 | 不设（它就是档案） |

**读的顺序 —— 这是三份里唯一需要背下来的纪律**：

1. **`now.md` 全文**（几十行，先知道自己接的是哪一手）
2. **`must-know.md` 全文**（最值钱的一页）
3. **`log.md` 只读尾部 30 行** —— "上次 / 昨天发生了什么"。要更早的，**用 grep 去翻**。

> ⚠️ **`log.md` 永远不整篇读。** 实测：一个角色干了两天，`log.md` 就到了 **136 KB
> （约 3–4 万 token）**。每次上岗全文读一遍，就是**每上一岗烧一次**，而且随天数线性涨。
> **这是这支队目前最贵的一笔开销，也是唯一必须靠纪律堵住的口子。**
>
> 让 grep 好用的唯一诀窍：**每条都带具体标识符** —— 文件名、函数名、命令、错误串。
> 千万别写"我们讨论过性能问题"这种没有锚点的话（grep 不到 = 没写过）。

**写 `must-know.md` 的两条硬规矩：**

1. **只写"读代码推不出来"的东西。** 实测：上下文文件对正确率的提升很小甚至**为负**
   （手写 +4%、自动生成 −3%，成本一律 +20%）；**唯一显著有用的场景，是那份信息本来无处可查**。
   能自己看出来的东西写进去，只是更贵、更容易出错。
2. **失效的不删，但替代项写在同一行：**

   ```
   ~~默认模型 deepseek-flash~~ ⚠️ 已失效 2026-09-18 → 见 deepseek-v4-pro（老板拍板）
   ```

   ⚠️ 依据是一条硬实证：**被标记失效的事实，在 5 个主流记忆系统里照常被检索返回，
   而且排名高于它的替代项** —— 结果 agent 照着已经作废的旧事实去做事。
   **"划掉但保留"等于没划掉。** 只有让 grep 命中的那一刻**同时看见两者**，才是安全的写法。

**每一次上岗，前四步固定**：读 `now.md` → 读 `must-know.md` → 读 `log.md` 尾部 30 行 → 读任务。
**收工前两步固定**：**重写 `now.md`** → 追加 `log.md`；**真的学到东西才动 `must-know.md`**。

> 队员每次都是全新的人，**这三份文件就是他的记忆**。这一条是队伍能连续工作的前提。

**谁保证这一页不腐烂**：流程位（阿玛拉）每天复盘时顺一遍 —— 合并重复、删掉不成立的、
补上缺的。⚠️ **但她量不了字数（她没有 shell）**，所以：

- **组长每天量一次，把数字给她**（`must-know` 多少字、`log.md` 多少 KB）。
- `must-know` 超 **2000 字** → 当天归并；`log.md` 超 **500 KB** → 原地按月开一节归档。
- **没有人在看的"上限"，和没有上限是一回事。**

**三条配套规矩**：

1. **`.team/` 必须写进项目的 `.gitignore`。** 第一次在某个项目开工时先确认这一条。
2. **交付前跑一次 `git status --short`**，确认 `.team/` 没被 git 看见 —— 这是
   "没往代码仓库里塞东西"的可执行检查。
3. **`.team/README.md` 里写明**：这里的东西不属于项目代码，不进版本库。

## 收工

一票活干完（或被打回）时，做五件事：

1. **逐条核对 S0 的验收口径**，说清哪条过了、哪条没过，**并写成验收记录落进 `.team/deliverables/<日期>/`** —— 老板看的是那里
   （2026-09-17：票 53 / 55 的验收记录都是**补写**的，因为没人盯着这一步）。
2. **每个上过场的人写自己的日志。**
3. **复盘按「天」做，不按「票」做**（用户 2026-09-17 当天纠正）—— 具体见下面那段。
   票收尾时**不**叫流程位；该叫的时候是**每天一次**。
4. **问一句："这次学到的东西该进哪份文件？"** —— 该进 `must-know` 的进 `must-know`；
   该改进工序的，交给流程位去提案。
5. **这一票的非阻塞条目**（评审给的、我自己发现的）**写进 `.team/leader/follow-ups.md`**（常设文件，一直在长）：
   每条要么有票、要么写明"为什么不修"；处理掉的标 ✅ 并写清**处置落在哪**。
   ⚠️ 2026-09-17 的来历：两份验收记录都在引用一份**根本不存在**的清单 —— 引用了却没有的东西，比不写更坏。

> **复盘的时间点（用户 2026-09-17 定；09-18 补明"什么时候做"）**：
> **每天一次，在开工时做、覆盖的是「昨天」那一整天**（老板 2026-09-18 原话：「复盘今天已经做过了，每天上工的时候复盘昨天的」）
> —— 票多就在同一份复盘里分节写，但**只叫流程位一次**。⚠️ **不是收工时做**。
> ⚠️ **触发是组长的常设职责**，不是等老板提醒。
> ⚠️ **强制点 2026-09-18 搬过一次（老板抓出来的）**：原先写的是「组长的完成报告里固定带一行『复盘：…』」——而**早上还没交报告** ⇒ 这条**永远不触发**（09-18 早上就是老板提醒的）。
> ⇒ 现在写的是：**组长每天开工第一步，读 `.team/leader/log.md` 的尾部** —— 那里固定留「待老板拍」与「开工先做」；复盘该不该补，**必须在那一行里**。
> 一条写不出「谁强制它」的规则就是建议 —— 至少让它落在老板看得见的报告里。
>
> ⚠️ **来历（别重复踩）**：上午的版本是「一票活收尾 = 复盘点」。**试了一天就被用户否掉**，原话是
> 「算了算了别让 amara 每轮复盘了，还是每天复盘一次吧，**我的 token 预算顶不住她这么烧**」。
> ⇒ 教训不是"复盘没用"，是**复盘的单位选错了**：一票的复盘要重读契约 / 评审 / 读数全套材料，
> 而一天几票时这些材料大半是重叠的 —— **按票复盘 = 同一份材料读好几遍**。
> ⇒ 以后要加任何"每次 X 就做 Y"的规矩，先算一句「**一天会触发几次**」。

## 附：这套工序的底气

哪些是**有实证支持**的，哪些是**从机制外推的判断** —— 分清楚，别把判断当事实：

**有实证**：小批量（100 行 / 400 行上限）· 评审者独立 + 测试与实现分离 ·
角色数控制在三个左右 · 没有中心化验证的架构更容易传播错误 · 迭代 3–5 轮后收益趋平 ·
覆盖率门槛会被"刷"。

**业内惯例、没有证据**：改动预算的具体格式 · "一页纸"要写多细 · 各道关的时间盒长度
—— 这些当可调参数，不要当定律。

**从机制外推的判断**（**如果上线后发现某一关从来没产出过东西，优先砍这几条**）：
评审只审机器管不了的 · S1 禁止预读实现 · 砍掉设计文档评审关 · 角色数上限三到四。
