# 这份预设是怎么设计的

**这份文件不进提示词、不注入任何会话。** 它是给维护的人看的：记清楚
「为什么这么写」，以及「写的时候依据的是哪个版本的事实」。

改任何一份会被注入的 markdown 之前，先读这一份。

## 一、六个队员的毛病，每一条都钉在既有实践上

队员的"毛病"不是编出来的性格缺陷，**是那个岗位真实会犯的错**，
而且每一条都指回工程守则或实例库里**已经写着的那一节**：

| 谁 | 她的毛病 | 岗位的经典失败模式 | 兜住它的既有实践 | 出处 |
| --- | --- | --- | --- | --- |
| **比娅**（产品） | 把"顺便"当成承诺 | 需求蔓延 | 只写解决当前问题的最小代码 · 只改必须改的地方 · **提交钩子卡"净增行数"** | 守则三、五；实例库一「体积」 |
| **佐西亚**（实现） | "代码自己会说话" | 只有作者知道为什么 | 注释全中文只描述现在 · **自定义 lint 规则强制"具名函数必须有说明"** · 只清理自己制造的问题 | 守则七、五；实例库四 |
| **玛尔塔**（测试） | 把"绿了"当成"对了" | 假通过 | **假通过清单** · 失败断言先怀疑断言 · **覆盖率门槛会被刷** · "静默失效的检查与通过的检查长得一样" | 守则二；实例库五、一 |
| **伊莫金**（评审） | 把"我更喜欢"当成"问题" | 偏好伪装成缺陷 | **lint 的定位：只开「错了就是错了」的规则** · 门禁已覆盖的东西不再重复看 | 实例库三、一；守则三 |
| **阿玛拉**（流程） | 给方向不给原文 | 复盘没有产出 | **新增纪律 = 新增检查，不写文字** · 写不出「谁强制它」的规则就是建议 | 守则一 |
| **Agenia**（组长） | 手快、爱顺手改 | 跳关 | 「不许自己干」四条 · 只修改必须改的地方 | 守则五；项目自己的行为规则 |

**为什么要这么钉**：一个岗位的"毛病"如果跟它的防线对不上，那条防线就是摆设。
反过来，**每条毛病都能指到一条已经存在的规矩**，说明这套设计是从真实工程里长出来的，
不是坐在那儿想出来的。

## 三、哪些是证据，哪些是判断

**有实证支持**（细节和来源见 `process.md` 末尾那一节）：五道关的划分 ·
测试与实现分离 · 角色数控制在三个左右 · 小批量（100 行 / 400 行上限）·

## 四、评审的写权限：一次有代价的取舍

**现状**：产品 / 审核 / 流程三个角色**只能写 `.team/` 下**的东西，而且**没有 shell**。
规则只有一个家 —— `persona-plugin/inject.js` 里的 `boundaryReason()`。
三个角色行的 `toolFilter` 只管"不许再招人"（`deny: [subagent_fork, workflow, ralph]`），
不再各自写一套。

（曾经写的是"把 `write`/`edit` 从评审的工具表里拿掉"。那是一段**有代价的取舍**：
拿掉她就写不了自己的日志，只能由组长代笔 —— 等于拿"评审者没有记忆"换
"评审者不能改代码"。角色边界做出来之后，这个取舍就不需要了。）

### 它是怎么认出"你是谁"的 —— 已实测

门禁拿到的是 `exec.agent`，而角色标记在**提示词装配**里。两者靠 agent id 接起来：
注入器在装配时看到标记，把 `agent.id → 角色` 记进一张表；门禁按 id 查。

**这张表成立的前提实测过了**：装配上下文里的 `scope` **就是** agent 对象，
`scope.id` 与 `exec.agent.id` 一致 —— 边界日志里的 `MAP <id> -> <role> hasSession=true`
就是它的物证。

**失败方向是往安全那边倒的**：认不出角色的 agent 一律放行。Leader 自己没有角色 →
永远不受影响；别的预设的 agent 也查不到 → 不受影响。

### 两个洞是队员自己撞出来的

第一版门禁**有两处漏洞，都是实测复现的**，不是推演出来的：

1. **`pwsh` 根本不在管辖范围。** 守卫只认 `write` / `edit` 两个工具名 ——
   同一个角色、同一个目录：`write` 被拒，`pwsh` 直接写进去。
   → 修法：办公受限的三个角色**整体没有 shell**。
   **用守卫按名字否，不用 `toolFilter`** —— 后者要按平台写 `pwsh` 或 `bash` 里的一个，
   写错另一个会以"未知工具"让整个组员**启动失败**（这条踩过）。
2. **守卫只看路径字符串，不做规范化。** `.team/product/../../x.txt` **含有** `.team/`
   这一段，于是放行，而它实际落在项目根。
   → 修法：先 `resolve(cwd, target)` 算出落点再判；cwd 取不到时相对路径**一律拒绝**，不猜。

修完复验五炮 —— 写自己地盘 / 写项目根 / 换 shell / 路径穿越 / 实现者对照 ——
全部符合预期，边界日志逐行对得上。

### 这张网还漏着什么

- **`hire`（临时外聘）不受限。** 他的说明书写着"不许动项目代码，**除非组长明确让你改**"——
  那个"除非"意味着他必须留着写权限。挡住他的是组长的派活，不是系统。
- **`dev` / `test` 不受限** —— 他们本来就要写源码和测试。
- **未来新增的写文件工具，这张网不认识。** `WRITE_PATH_ARGUMENT` 就是全部的管辖范围；
  加工具时要一起改。

## 五、项目往前走之后，怎么重新对一遍

`TavernGame` 是这份预设的素材来源，它会继续变。**它一变，上面的对照表就可能过期。**

重新核对的清单（每条都要跟到具体文件，不要凭印象）：

1. `.githooks/pre-commit` —— 还是不是 16 项？顺序变了没有？`SIZE` 常量是多少？
2. `vitest.config.ts` —— 覆盖率门槛和统计范围变了没有？
3. `doc/DESIGN.md` —— 决定编号写到几了？有没有新的"大原则"级决定？
4. `AGENTS.md` 前 20 行 —— 行为规则和反过度工程那两节改了没有？
5. `.agents/skills/` —— 有没有新增 skill？`verification` 里的假通过清单有没有加新形态？
6. `git log --oneline -20` —— 最近有没有"用户拍板"类的决定，是那种会改变规矩的？

**核对完就把日期和提交号写回这一节。** 不写日期的事实，等于过期的事实。
